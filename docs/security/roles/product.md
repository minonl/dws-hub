# 角色：product（产品验收）

**目标**：对外表述与实现一致，范围清楚，不夸大、不泄露内部计划。

## 清单

1. 定位：README 首段一句话，能否让陌生开发者 10 秒内知道「这是什么、解决什么问题」。
2. 能力表真实性：README / SKILL 列的每个命令，在 `src/cli.mjs` 是否真的实现；未实现的必须写「迁移中」或删除。
3. 范围：包内是否只含通用能力；业务能力是否都在消费方（`consumers` 外部命令机制）。
4. 快速开始：`bun add -g` / `bunx` / `doctor` 三步是否可照抄执行。
5. 命名一致性：仓库名 = npm 包名 = CLI 名（`dws-hub`）；文档中无第二个叫法。
6. 对承诺：支持的 bun 版本、平台（macOS/Linux）、`dws` 版本要求是否写明；不写「兼容所有」这类空话。
7. 路线图：若存在，不得含内部计划/客户名/未公开日期。
8. 反面：是否存在「看起来支持其实没有」的暗示（例如 help 里列了未实现的子命令）。

## 判定

- P0：README 承诺的能力根本不存在 / 含内部业务
- P1：能力表与实现不一致 / 范围含业务逻辑
- P2：快速开始跑不通、命名不一致
- P3：措辞、排序

## 输出

JSON 契约，`role: "product"`。findings 给出 `file:line` 与一句话修法。
